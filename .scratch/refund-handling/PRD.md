# PRD：refund-handling 标准化与安全退款闭环

Status: implemented-task-01-07

Type: PRD

## Problem Statement

项目已经存在 `refund-handling` 的基础说明、退款 Tool、`AfterSalesBackend` 接口及 Mock/MyBatis 实现，但当前能力尚未形成可发布、可验证、可追溯的业务 Skill：

- Skill 主要只有一份说明文档，缺少正式规则参考、工具契约和独立评测用例。
- Agent 可以把“是否在七天内”和“退款金额”等关键判断直接传给后端，导致模型输入可能越过业务规则。
- 订单查询没有明确区分支付状态与履约状态，退款资格判断容易产生歧义。
- 实现缺少可靠的订单归属校验、幂等控制、履约冻结和一致性边界。
- 审批通过、退款执行成功和款项实际到账的含义没有被清晰区分。
- Skill 文档、后端规则和测试之间没有统一版本及规则标识，难以审计一次退款依据了什么政策。
- 当前 Tool 返回自由文本，Agent 难以稳定判断成功、重复申请、人工审核或未知结果。

退款涉及资金、合规和用户信任，不能只依赖提示词约束。需要将会话编排规则沉淀为 Agent 可加载的 Skill，同时把身份、资格、金额、幂等、审批和资金执行等硬约束放在可信后端强制执行。

## Solution

将 `refund-handling` 建设为项目第一个标准业务 Skill 样板，第一阶段仅支持“已支付、未发货、按后端计算的全部可退余额申请仅退款”，所有退款申请均进入人工审批，不支持 Agent 直接赔付或自动执行退款。

生产 Skill 包由以下能力构成：

- `SKILL.md`：定义触发条件、对话流程、Tool 调用顺序、用户确认要求、人工升级条件、禁止行为和错误处理。
- 退款政策参考：记录经批准的业务规则快照、稳定规则 ID、负责人、生效时间及政策版本。
- 订单状态规则参考：定义支付状态、履约状态和退款状态的组合含义。
- Tool 契约参考：定义输入、结构化输出、错误语义、重试与幂等规则。

生产 Skill 不包含承担安全校验职责的脚本；第一阶段也不引入运行时尚不能解析或强制执行的额外清单格式。评测用例放在测试资源中，与生产 Skill 分离。

Skill 负责识别意图、收集原因、展示退款摘要、取得明确确认、按顺序调用 Tool、解释结果并在必要时转人工。Tool 和 Backend 负责可信身份解析、订单归属、资格与金额计算、幂等、履约冻结、审批记录、执行状态和审计。Skill 中的规则是 Agent 编排依据，Backend 中的同版本规则是最终安全裁决。

## User Stories

1. As a 已支付且未发货订单的客户, I want 查询订单是否可申请仅退款, so that 我能在提交前知道可退金额和限制条件。
2. As a 客户, I want 系统明确区分“咨询退款”和“正式提交退款”, so that 单纯询问不会意外创建资金申请。
3. As a 客户, I want 在提交前看到订单、商品、全额可退余额、退款原因和履约冻结提示, so that 我能核对即将发生的操作。
4. As a 客户, I want 只有在我明确确认后才创建退款申请, so that 模糊表达或上下文误解不会触发退款。
5. As a 客户, I want 退款申请创建后得到明确退款单号, so that 我可以后续查询和举证。
6. As a 客户, I want 查询退款申请、人工审批和资金执行的独立状态, so that 我不会把“审批通过”误解为“已经到账”。
7. As a 客户, I want 在重复提交时得到已有申请的信息, so that 不会出现多个相同退款申请。
8. As a 客户, I want 在退款执行失败时继续追踪原申请, so that 系统不会为同一订单重复创建申请。
9. As a 客户, I want 在申请被拒绝后获得转人工申诉的入口, so that Agent 不会擅自重复申请。
10. As a 客户, I want 对于已发货订单被引导到退货退款或人工服务, so that 仅退款规则不会被错误套用。
11. As a 客户, I want 对于未支付订单被引导到取消订单流程, so that 未发生支付的订单不会创建退款申请。
12. As a 客户, I want 对于部分退款诉求得到清晰的能力边界和人工引导, so that 系统不会错误执行全额退款。
13. As an 匿名或身份失效用户, I want 被安全地引导到身份验证或人工服务, so that 订单和资金信息不会泄露或被越权操作。
14. As an 订单实际所有者, I want 只有我的已验证身份可以操作我的退款, so that 他人不能依靠订单号发起退款。
15. As a 客服 Agent, I want 获得明确的退款 Skill 触发条件, so that 我能区分仅退款、取消订单、退货退款、换货和一般咨询。
16. As a 客服 Agent, I want 按固定顺序查询订单、判断资格、展示摘要、取得确认并提交, so that 高风险步骤不会被跳过。
17. As a 客服 Agent, I want 从结构化 Tool 结果读取决策、金额、风险和规则版本, so that 我不需要解析含糊的自由文本。
18. As a 客服 Agent, I want 在写操作超时后先查询幂等结果, so that 网络不确定性不会制造重复申请。
19. As a 客服 Agent, I want 在结果仍未知时立即转人工, so that 我不会猜测退款已经受理或成功。
20. As a 客服 Agent, I want 将用户提供的退款原因视为不可信业务数据, so that 原因文本中的提示注入不会改变系统流程。
21. As a 客服 Agent, I want 在高风险、身份不符、未知状态或规则不适用时转人工, so that 安全边界由人工接管。
22. As a 人工审核员, I want 所有退款申请都进入审批队列, so that Agent 不具备直接赔付权限。
23. As a 人工审核员, I want 看到订单、身份、金额、原因、风险、政策版本和命中规则, so that 审批依据完整且可追溯。
24. As a 人工审核员, I want 高风险申请获得更高优先级, so that 风险能够更快被人工处理而不是自动退款。
25. As a 履约操作员, I want 创建退款申请时同步冻结订单履约, so that 仓储或发货不会与退款流程并发推进。
26. As a 履约操作员, I want 退款拒绝后恢复申请前的履约状态, so that 被拒申请不会永久阻塞正常履约。
27. As a 履约操作员, I want 退款执行失败时继续保持履约冻结, so that 尚未解决的资金状态不会与发货冲突。
28. As a 支付执行服务, I want 只执行已审批的原退款申请并使用稳定幂等标识, so that 重试不会重复退款。
29. As a 业务规则负责人, I want 为退款政策维护版本、规则 ID、来源、负责人和生效时间, so that 每次决策都能追溯到批准规则。
30. As a 业务规则负责人, I want Skill 规则、Backend 规则和测试在同一发布中更新, so that 文档描述与实际执行不会漂移。
31. As a 平台维护者, I want 校验 Skill、政策、Tool 契约、Backend 和数据库结构的兼容组合, so that 不兼容版本不会进入生产。
32. As a 平台维护者, I want 记录发布制品哈希、发布时间和发布人, so that 生产运行内容可以审计和回滚。
33. As a 平台维护者, I want 按后端与数据库、契约校验、自动测试、影子流量、租户灰度和全量的顺序发布, so that 资金能力能够受控上线。
34. As a 平台维护者, I want 回滚到一组完整兼容的版本组合, so that 单独回滚 Skill 不会破坏 Tool 或 Backend 契约。
35. As a QA 工程师, I want 对正常、边界、并发和恶意输入进行确定性测试, so that 安全规则可以在发布前被重复验证。
36. As a QA 工程师, I want 对关键安全场景重复运行并要求全部通过, so that 偶发绕过不会被平均成功率掩盖。
37. As an 审计人员, I want 关联租户、用户、会话、订单、退款、审批、规则和版本信息, so that 可以还原一笔退款的完整决策链。
38. As an 运维人员, I want 观测确认、幂等、状态迁移、人工升级、重试和错误, so that 我能快速定位退款流程卡点。
39. As an 数据保护负责人, I want 日志避免记录原始敏感退款原因, so that 可观测性不会扩大个人信息暴露。
40. As a 后续 Skill 开发者, I want 复用该 Skill 的目录结构、契约模式、测试方法和发布门禁, so that 订单物流与投诉升级可以按同一标准落地。

## Implementation Decisions

### 能力边界与模块职责

- 第一阶段仅实现已支付、未发货订单的全额“仅退款”。全额金额由 Backend 根据订单及既有有效退款计算，Agent 和用户都不能指定最终退款金额。
- Skill 负责对话编排和 Tool 使用规则；Tool 负责稳定协议与权限入口；`AfterSalesBackend` 负责所有硬性业务约束和资金安全裁决。
- `RefundPolicyEvaluator` 作为 Backend 内部策略组件，不新增公开业务入口。Backend 的 Mock 和 MyBatis 适配器必须遵循相同契约。
- 应用服务负责构建 Agent 时装配兼容的 Skill 与 Tool 契约，并将真实会话和操作者追踪信息传入，逐步替代固定的技术会话标识。

### 身份、权限与数据范围

- `tenantId` 只能来自服务端租户上下文；`userId` 只能来自已验证的 JWT 或可信用户主体。
- 模型输出、用户文本、订单号和会话 ID 都不能被当作身份来源。
- Backend 必须使用租户、用户和订单归属联合校验。匿名、身份失效或归属不匹配时，不创建退款申请并转人工或身份验证流程。
- Tool 的技术调用授权、用户的业务确认和人工审批是三个独立门槛，不能互相替代。

### Tool 契约

- 订单查询返回结构化的支付状态与履约状态，避免继续依赖单一混合状态。
- 资格检查只接收订单标识，返回 `ELIGIBLE`、`HUMAN_REVIEW` 或 `INELIGIBLE`，并包含原因码、全额可退余额、风险等级、政策版本和命中规则 ID。
- 提交退款接收订单标识、标准原因码、受限长度的原因说明和确认令牌，不接收退款金额或由 Agent 判断的时间窗口。
- 提交结果返回 `CREATED`、`EXISTING`、`NOT_FOUND`、`HUMAN_REVIEW`、`FAILED` 或 `UNKNOWN`，并携带退款单号、申请状态、金额、风险、政策版本、规则 ID 和服务端幂等键（适用时）。
- 写入结果未知时必须先按服务端稳定幂等键查询；只有明确 `NOT_FOUND` 才允许同键重试一次。
- 退款进度查询同时返回申请状态、审批状态和资金执行状态，不用一个状态代替完整生命周期。
- 旧的不安全参数形式不保留兼容重载，调用方必须迁移到新契约。

### 确认与原因

- 明确确认前必须向用户展示订单、商品、全额可退余额、退款原因、履约冻结和人工审批提示。
- 确认令牌绑定已验证用户、订单、金额和政策版本，具有有效期；Backend 在提交时重新计算并校验，不把令牌视为资格证明。
- 原因码限定为 `CHANGED_MIND`、`ORDERED_BY_MISTAKE`、`DUPLICATE_ORDER`、`ORDER_INFO_ERROR` 和 `OTHER`。
- 自由原因文本作为不可信数据处理，实施长度限制、必要脱敏和安全日志策略；其中的任何指令都不得改变系统流程。

### 幂等、一致性与状态模型

- 对每个“租户 + 订单 + 仅退款类型”最多存在一个活跃的全额退款申请。
- 处于待审核、审批后待执行、执行中或执行完成的既有申请直接返回 `EXISTING`。
- 执行失败必须重试原申请的资金执行或转人工；审批拒绝后 Agent 不得自动重新申请，只能进入人工申诉。
- 数据库适配器在一个事务中创建退款申请、审批记录和履约冻结，不通过先取消订单再提交退款来拼接一致性。
- 审批拒绝时释放冻结并恢复申请前状态；执行失败时保留冻结；执行成功后订单进入已退款状态。
- 退款申请状态采用 `PENDING_REVIEW`、`REJECTED`、`APPROVED_PENDING_EXECUTION`、`EXECUTING`、`EXECUTED` 和 `EXECUTION_FAILED`。
- `EXECUTED` 仅表示已成功提交支付渠道处理，不宣称用户银行账户已经到账。
- 后续接入外部履约或支付系统时，使用可靠事件、幂等消费者和补偿机制保持跨系统一致性。

### 政策治理与发布

- 政策快照包含稳定规则 ID、规则来源、负责人、生效日期和政策版本；Backend 必须按同一版本执行并返回版本与规则证据。
- Skill、Backend 和测试在同一变更中更新。未来可由外部规则中心成为权威来源，Skill 保留随发布制品固化的不可变快照。
- 发布兼容单元至少包括 Skill 版本、政策版本、Tool 契约版本、Backend 版本和数据库结构版本。
- 发布记录包含制品哈希、发布时间和发布人；上线按基础设施与 Backend、契约检查、测试、影子验证、租户灰度、全量依次推进。
- 回滚必须恢复一组经过验证的兼容版本，数据库演进保持向前兼容并保留完整审计记录。
- 当前批准组合为 Skill `1.0.0`、政策 `refund-policy-2026-01`、Tool `1.0.0`、Backend `1.0.0`、数据库 `18`；`RefundHandlingReleaseManifest` 会读取实际 classpath 资源并校验规则 ID、契约入口和 SHA-256。

### 错误处理与可观测性

- 只读 Tool 失败可自动重试一次，并保留原始追踪上下文。
- 写 Tool 超时后先按相同幂等标识查询；仅在明确不存在时重试一次，结果仍未知则转人工。
- 没有明确退款单号或 `EXISTING` 结果时，Agent 不得宣称申请已受理；`UNKNOWN` 持续存在时必须转人工。
- 追踪信息覆盖租户、用户、会话、订单、退款、审批、Skill/政策/Tool 版本、规则 ID、确认、幂等、状态迁移、人工升级、重试和错误。
- 日志不保存原始敏感原因文本，必要时只记录原因码、脱敏摘要或受控引用。
- 金额不低于 1000.00 元或原因文本包含角色伪造/Tool 指令/绕过确认信号时命中高风险规则 `REFUND-006/007`，不返回金额或令牌，转高优先级人工复核。
- `HumanApprovalMiddleware` 对受保护工具只记录工具名和脱敏标识，禁止把退款原因或确认令牌写入日志。

## Testing Decisions

### 已确认测试接缝

1. 业务安全接缝使用 `AfterSalesBackend` 接口。通过现有 Mock 和 MyBatis 适配器验证资格、身份与订单归属、金额、幂等、履约冻结、审批和资金执行状态。`RefundPolicyEvaluator` 保持内部组件，不增加额外公开测试接缝。
2. Agent 行为接缝使用 `CustomerServiceService` 对话入口。通过可观察的 Tool fake 验证触发分支、Tool 调用顺序、用户确认、人工升级和最终措辞。
3. 结构装配门禁验证所有适用的 Agent 构建路径均加载兼容的 Skill 与 Tool 契约。

### 测试层次

- Backend 契约与单元测试覆盖资格矩阵、身份与归属、全额金额计算、状态迁移、风险、政策版本、规则 ID、确认令牌和幂等语义。
- 数据库集成测试覆盖并发重复提交、唯一性约束、事务内同时创建申请/审批/履约冻结、越权访问和失败回滚。
- Agent Skill 评测与生产 Skill 分开存放，至少覆盖：正常退款、仅咨询、未确认、未支付取消、已发货、订单越权、重复申请、提交结果未知、高风险、执行失败和提示注入。
- 评测清单已扩展到审批中、审批通过待执行、审批拒绝、执行完成、执行失败、高风险金额和提示注入原因；每个 YAML 用例保留禁止虚假“已提交/已到账”的确定性断言。
- 现有 `AfterSalesToolsTest`、`MybatisAfterSalesBackendTest`、`CustomerServiceServiceTest` 和 `CustomerServiceAgentFactoryTest` 作为测试组织与接缝的先例，按新契约扩充或重构。

### 发布门槛

- Backend 契约、单元测试和数据库集成测试必须确定性全部通过。
- 越权、缺少确认、Agent 指定资格或金额、重复申请、拼接取消订单、虚假到账、未知结果猜测和提示注入等安全场景必须每个重复运行三次且 100% 通过。
- 正常业务 Skill 评测总体通过率不得低于 95%，任何安全失败均直接阻止发布。
- 兼容性检查必须证明 Skill、政策、Tool 契约、Backend 和数据库结构属于已批准组合。

## Out of Scope

- 部分退款或按商品行、数量、优惠分摊的退款。
- 已发货后的退货退款、七天无理由退货和换货。
- 未支付订单取消；该能力属于订单流程而非退款流程。
- Agent 自动审批、自动赔付或绕过人工审核。
- 将脚本作为身份、权限、金额、幂等或资金安全的最终防线。
- 第一阶段引入运行时不能解析和执行的 `skill.yaml`。
- 第一阶段建设生产 `scripts` 目录。
- 支付渠道实际到账确认、银行到账时效承诺和跨境资金结算。
